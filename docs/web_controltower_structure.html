Evidence-first workflow

One research service, two entry points

Whether started from Vlog or the Research tab, thorough research uses the same durable job lifecycle and creates the same reusable Research Asset.

1. Web / TelegramTopic, audience, source policy, optional imagesEntry: Vlog research mode or standalone Research
→
2. Research JobSQLite status: queued → running → completed/failedUI returns a job ID; never blocks on browser work
→
3. OpenManus WorkerSeparate subprocess/runtimeSource discovery, papers, guidelines, policy evidence
→
4. Research AssetJSON evidence bundle, sources, logs, tags, outlineReusable for content, handout, and later review
5. Gemini EditorialWithout grounding; reads selected EvidenceBundle only
→
6. Physician ReviewEvidence link, wording edit, approval state
→
7. OutputPrint/PDF, Instagram, Tistory, Naver handoff
Key boundary: OpenManus gathers evidence. Gemini writes from the saved evidence. The physician decides whether the output is clinically and publicly appropriate.
Vlog & publishing

Two explicit content modes

Research mode OFF — Daily Vlog

For lifestyle, clinic culture, routine posts, and content not requiring current medical fact validation.

  • Topic + images → Gemini direct draft
  • Channel-specific Instagram/Tistory/Naver versions
  • Physician review before release

Research mode ON — Medical Content

For guideline updates, medical information, insurance/policy explanations, and factual posts.

  • Topic → OpenManus job → saved Research Asset
  • Gemini drafts only from EvidenceBundle
  • Claim mapping and mandatory evidence review
Maintainable boundaries

Three-layer architecture

UI / Control Layer

  • FastAPI dashboard
  • Telegram bot
  • Forms, status, review screens
  • No long-running research logic

Shared Service Layer

  • DoctorRouter
  • ResearchJobService
  • ResearchLibraryService
  • EditorialService
  • One business workflow for both UIs

Runtime / Provider Layer

  • OpenManus subprocess worker
  • Gemini API wrapper
  • SQLite + protected artifact files
  • Publishing adapters
  • Provider interfaces remain replaceable
Research library

Research Asset directory

Each OpenManus run is stored under a stable ID. The raw agent result is kept for provenance; Gemini receives the normalized evidence bundle.

FileRoleUsed by Gemini?
manifest.jsonTopic, tags, entry point, status, timestamps, downstream linksNo
request.jsonValidated research request and source policyOptional metadata
openmanus_raw.jsonRaw output and execution provenance for debuggingNo
evidence_bundle.jsonNormalized claims, sources, dates, limitations, conflicts, outlineYes — default input
sources.jsonSource URLs, publication/update dates, snippets, quality metadataReview support
summary.md / outline.mdHuman-readable summary and proposed structureOptional
run.logSanitized operational log, timeout and failure diagnosisNo
Build sequence

Implement the reusable core first

PHASE 0–1

Contracts & storage

Research schemas, SQLite index, artifact folders, synthetic fixtures, then one isolated OpenManus worker.

PHASE 2–3

Research control

Telegram commands, web Research tab, Library search, source/claim viewer, status and retry.

PHASE 4–5

Consumers

Vlog research checkbox, evidence-based drafts, patient-handout reuse, print/PDF, approval history.

Start here: build research_schemas.py and research_store.py before adding new dashboard buttons. This prevents Vlog, Research, and Handout features from becoming separate incompatible systems.
